# 数学建模协作

识别本轮目的，设计合理、高效的分工，让每位队员及其 Codex 知道为什么这样分、自己怎样开始、最后交什么。把信息沟通和反复对齐的成本也纳入分工设计。

本 Skill 负责安排分工、帮助接手、简明反馈。模型是否成立、数据和结果是否可靠、研究是否继续，由团队或相应专业 Skill 判断；这里根据已有判断组织工作。专业复核可以是一项被分配的任务，不是每轮协作的固定手续。

## 先理解这一轮要达到什么目的

先读项目规则、已有题意和当前进度，结合对话判断本轮目的。只补读会影响分工的材料，不要求所有人重新消化全部研究记录。

已有信息充分时，直接说明对目的的理解并提出分工。目的不清，或人员、时间、资源等缺口会实质改变安排时，先用一轮集中的询问补齐；不要让用户填长表，也不要重复询问已经明确的信息。分工得到确认后直接整理接手说明，不再重复确认。

## 按目的设计能独立推进的分工

选择能服务本轮目的的协作方式，解释这样安排的收益。以下是例子，不是必须套用的分类或固定人数：

| 目的 | 可能的分工方式 |
| --- | --- |
| 探索 | 各自研究有实质差异的路线，独立形成候选后汇合，避免一开始就共享同一个思路限制。 |
| 排查或辨析 | 分别寻找支持证据、反例或适用边界，必要时安排一位汇总分歧；最终结论交由团队或专业判断形成，不预设哪方正确。 |
| 精修 | 以共同的大骨架为起点，分别负责几个相对独立的方面，明确允许改动的范围与共同约定。 |
| 推进实现 | 按能够独立完成的任务划分，每位负责人交出完整、可接用的一项成果。 |

可以组合或采用其他方式。不固定“建模手、编程手、论文手”，也不为凑齐人数硬拆任务。根据队员已说明的能力、时间和可用资源安排，不自行编造人员条件。

提出分工前，逐项考虑：负责人凭当前已有材料能否立即开始，能否在本轮独立完成，产出怎样服务共同目的。不要机械拆成“一个人写公式，另一个等着翻译成代码”。对确实存在的先后依赖，先安排必要前置工作，并给其他人安排独立任务；不能把等待未来成果的任务描述成可立即并行。

只统一协作必需的起点、接口和编辑范围，给每位负责人保留完成任务的方法选择空间。探索时路线差异可以是刻意设计的；共享文件需要同时修改时，约定各自范围或临时整合者，避免并发覆盖。

先向人清楚说明本轮目的、分法及理由，再说明每项任务的起点与交付。独立账号没有天然共享的在途任务；沿用队员已告知的认领情况，区分建议与已确定分工，不把建议说成已通知或已认领。

## 写清接手说明，让 Codex 和人都能读懂

分工确定、准备交接时，在仓库已有 handoff 或协作 Markdown 中写明；没有合适位置时，在现有文档目录建立一份分工说明。不另外建立看板、状态体系或每人一套重复文档。

说明应足以让未参与前序对话的队友及其 Codex 开始工作，覆盖：

- **共同背景和本轮目的**：正在解决什么问题，目前已有何种起点，这轮希望推进什么。
- **整体安排及理由**：各人负责什么，这样分如何服务目的，各任务之间有什么关系。
- **每人的任务**：具体问题、可直接使用的材料、必要约定和编辑范围、预期交付及反馈位置。

详细程度以接手需要为准：共享背景只写一次，技术细节指向仓库中的具体文件或章节，路径相对项目根目录。若交接涉及程序接口，写清必要的输入输出、单位和失败表示；不涉及的任务不用填这些字段。不要把一份分工说明扩成完整研究记录。

接手的 Codex 先读这份说明及本任务必要材料，再向队员简明解释“我们为什么做这一轮、整体怎样分、我负责什么、最后交什么”。不要求人先读完技术细节，也不重复复述所有资料。

做一次轻量检查：任务是否清楚，引用的关键文件是否能取得，是否缺少明显的启动条件。缺什么就说明并补齐；这一步不默认要求复算、成果凭据或独立反驳。若任务中发现影响分工的新依赖，只向受影响的人说明所缺条件和安排变化，不让全队重复对齐。

## 路线完成后简明反馈

成果可以是思路、推导、反例、代码、修改建议或计算结果。沿用原任务的交付约定，把详细成果与必要依据留在仓库，反馈只保留队友需要知道的内容：

- 做了什么、得到什么，以及对共同问题有什么帮助或限制。
- 详细成果在哪里；如有下一位需要处理的事项，明确需要什么配合。

优先用一小段话或少量条目说明，不完整复述研究过程，不手抄已有结果，也不要求所有人重新阅读全部材料。没有需要协作的事项就不追加对齐会议或确认步骤。论文写作者及其他队友可自行用 AI 按仓库记录查阅细节，无需专设论文交接流程。

## 传递方式

赛前可以沿用GitHub项目仓库与独立Skills仓库：当前任务分支、验证后PR、明确接收人。先确认真实Git状态和权限；无.git档案不能当作checkout，已有成果不可被远程旧模板覆盖。

正式赛期先读当届官方规定。2026规则明确限制GitHub等平台上的赛题交流，不能自行认定私有仓库豁免。当前保守做法是赛前安装冻结技能，赛期只用本地Git和队内文件传递；相关限制与离线命令见 [队内交接](references/team-transfer.md)。无规则冲突时按团队已授权的工具行事，不把审批变成每一步的仪式。
